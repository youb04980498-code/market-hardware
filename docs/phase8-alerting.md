# Phase 8 operational alerting

Alerts are persisted in the existing separate `market_analytics` database, not a fifth business schema in `market_db`. Deterministic UUID/identity prevents duplicates. ACTIVE, ACKNOWLEDGED and RESOLVED states include timestamps; staff actions have an append-only action record. Acknowledgement survives recurring observations. Stock-condition recovery resolves the alert; a recurring unsafe stock condition reopens the same identity. Payment incidents stay resolved after operator resolution, even when historical failed payments are re-exported.

Sources: low stock and capacity reconcile the authoritative read-only Inventory snapshot; genuine FAILED payment rows reconcile authoritative Payment exports. The existing Spark refresh invokes reconciliation, so these are eventually consistent with the snapshot cadence. They are not synchronous safety controls. Inventory's original transactional guards remain authoritative.

Order spikes use the same Spark worker and Kafka bus, with a separate checkpoint `checkpoints/order_spikes_v1` so existing ingestion state is never reset. Five-minute event-time windows use a ten-minute watermark and watermark-bound `event_id` deduplication. The second query only processes `market.orders.v1`; it does not replace the financial pipeline. Its first start begins at latest offsets, then resumes its retained checkpoint. Events behind the watermark are excluded from this bounded operational detector; the existing raw ingestion still retains late transport events. Duplicate suppression is bounded by the watermark; payment/stock alert identities remain durable indefinitely.

Defaults, configured through Compose environment/.env: `ANALYTICS_LOW_STOCK_THRESHOLD=5`, `WAREHOUSE_SATURATION_PERCENT=90` (strictly greater than), `ORDER_SPIKE_BASELINE_PER_5M=5`, `ORDER_SPIKE_FACTOR=3`, `ORDER_SPIKE_MIN_COUNT=10`. The baseline is an explicit local demonstration assumption, not an automatically learned historical baseline. A spike requires at least max(minimum,baseline*factor) orders.

Staff endpoints: GET `/api/analytics/alerts` (optional status and bounded limit), GET `/api/analytics/alerts/{uuid}`, POST `.../acknowledge`, POST `.../resolve`. Customers receive 403; anonymous callers receive 401. Direct detail reads and actions remain role protected. Alerts deliberately contain logical references and failure category, never payment credentials. Abandoned carts remain deferred because client-side cart state has no reliable durable event timestamps.

Infrastructure alerts are separate Alertmanager incidents. Defaults in `infrastructure/prometheus/rules.yml`: service down 1 minute; >5% HTTP errors for 2 minutes; p95 >2 seconds for 2 minutes; Kafka lag >100 for 2 minutes; analytics age >180 seconds for 1 minute; unhealthy pipeline 1 minute; positive lag and zero Spark input rate for 2 minutes. Edit the tracked rule configuration to change thresholds; validate with promtool. The local receiver retains incidents in Alertmanager; external paging/email is not configured.
