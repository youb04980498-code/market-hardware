# ADR 0008: read-only 3D world and Kafka invalidations

Status: implemented on `3d-test-branch`, 2026-10-24. This experiment does not change V3 requirements or business state machines.

Keep the original demo at `/admin/3d-store`. Add the desktop-only recorded-data world at `/admin/3d-world`. Reuse the existing React/Three renderer, materials, lettering, character model, camera and error boundary. Browser geometry is an illustrative read model, never a business command interface.

Introduce one optional `world` Compose service: an authenticated HTTP composer plus a single Kafka-consumer thread. It has **no database credentials, database connection, persistent projection or business-write endpoint**. It forwards the requesting staff token to existing public APIs and rechecks active Auth sessions. Inventory and Payments add small staff-only, schema-owned read endpoints to avoid N+1 requests or private cross-service queries. No migrations or grants are required.

The separate `market-3d-world-v1` group consumes existing Orders/Inventory/Payments topics. It validates the envelope identity/source/version/timestamp, suppresses recent identical event IDs, counts conflicts/poison records and only increments an invalidation revision. It does not interpret payloads as final order/payment/stock state. Duplicate, conflicting or older events therefore cannot roll a financial state backward. Identical duplicates older than the bounded 4096-ID cache can request an extra read, with no business side effect.

Offsets are explicitly committed synchronously **after** processing or deliberate poison rejection, with automatic commit and automatic offset storage disabled. A commit failure causes retry/rejoin from the last committed position. Rejections are diagnostic counters, not a durable dead-letter queue. The bridge is disposable: every SSE connection/reconnection mandates a complete authoritative HTTP read, and periodic reads cover lost notifications, process restarts and catalogue changes without commerce events. No end-to-end exactly-once or complete event-history replay guarantee is claimed.

SSE contains revision/connection diagnostics and sanitized event identity/type/time, never raw payloads, names, emails or bearer secrets. Authentication uses the Authorization header rather than URL parameters. Streams rotate after about a minute, recheck Auth every ten seconds and expose broker loss separately from HTTP availability. The browser has a heartbeat deadline, reconnect backoff, offline handling, coalesced sequential snapshot reads and a fifteen-second reconciliation timer. A revoked session stops receiving data on the next Auth recheck.

All coordinates, racks, routes, parcels and order figures are **synthetic placements / logical representations**. Stock quantities, identities, payment states and order statuses come from owning APIs. No physical location, packing operation, vehicle movement or customer identity is inferred. Live carts are unavailable because no server-side cart/session telemetry exists; the original explicit DEMO retains synthetic shoppers and carts. Shipping/delivery visuals only use recorded SHIPPED/DELIVERED states; this adds no shipping or payment mutation API.

The city uses one ground plane and one persistent Canvas for Commercial, Industrial, Logistics and Business districts. Camera focus replaces scene switching, avoiding context teardown during navigation. Existing store, checkout, warehouse and fulfillment components are reused. Virtual Business offices show existing API reads, with monitoring fetched independently from core snapshots. A clearly labeled opt-in DEMO layer adds pedestrians, carts and circulating vans without changing business records.

Practical limits: one worker/process per bridge instance, latest 100 orders per snapshot, first 100 catalogue products, paginated stock reads, at most five warehouse buildings/24 stock objects per warehouse/24 packages/eight live order figures rendered simultaneously. All warehouse records remain selectable through the list, with test records explicitly marked. These bounds, source freshness and missing data are exposed in the UI. Snapshot composition is not a distributed transaction. More replicas or a durable replay product would require a separate design.
